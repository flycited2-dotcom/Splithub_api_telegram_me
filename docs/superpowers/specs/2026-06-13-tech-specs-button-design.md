# Спека: кнопка «Добавить характеристики» в боте-меню

**Дата:** 2026-06-13. Контекст проекта — `CLAUDE.md`. Эта спека согласована с владельцем
(набор характеристик и UX выбраны им явно).

## Context (зачем)

В интерактивном боте (`stock_report_bot/bot.py` + `menu.py`) владелец проходит
Поставщик → Бренд → Серия → % и получает список позиций серии с ценой-с-наценкой
(готов к пересылке клиенту). Не хватает «продающего» блока: ключевых характеристик,
которые выделяют серию среди других (инвертор, класс A+++, работа до −15 °C, Wi-Fi и т.п.).
Цель — по желанию добавлять такой блок-цитату к результату, не меняя стандартный вывод.

## UX (v2 — по фидбэку владельца после теста)

- После выбора % показывается экран выбора с двумя кнопками: **✅ С характеристиками** /
  **📄 Без характеристик** (+ ⬅ Назад к выбору %). Callbacks: `gs|…` / `gp|…`.
- **Без характеристик** (`gp`) → итог как раньше: фото + список с ценами.
- **С характеристиками** (`gs`) → блок-цитата вклеивается в КОНЕЦ того же итога: фото +
  список + характеристики прилетают ОДНИМ сообщением (готово к пересылке клиенту;
  поставщик/наценка не раскрываются). При переполнении подписи 1024 — фото с первым куском,
  остальное текстом; цитата (`<blockquote>`) идёт единым блоком и не рвётся.
- Реализация склейки: `specs.build_specs_block(...)` → строка, передаётся в
  `menu.build_priced_message(..., extra_block=...)`. (Прежний вариант v1 — отдельная кнопка
  «➕ Добавить характеристики» под результатом и отдельное сообщение — заменён этим.)

## Уровень: общий блок на серию

Качественные признаки (инвертор, Wi-Fi, класс, −15 °C, фильтры) у серии одинаковы — берём
у представительных позиций серии. Числовые (шум/гарантия) — у первой позиции с непустым
значением. Перебираем все nc_code серии и для каждого признака берём первое
непустое/утвердительное значение.

## Источник данных

БД сайта (read-only): `catalog_producttech pt` → `catalog_techspec ts` (по `spec_id`) →
`catalog_product p` (по `nc_code`). Новый запрос `db.fetch_tech_values(nc_codes)`: по списку
nc_code серии вернуть пары `(title, value)`. Запрос ленивый — только при нажатии кнопки (редко).

**УТП (#30):** для Русклимата — из tech-поля «УТП» (в БД). Для Бриза поле `utp` синк сайта
НЕ кладёт (в модели товара его нет) → берём из Бриз API `/products/` тем же ключом
(`breez.fetch_breez_utp_by_nc`, кэш TTL в боте), как опт-цену. `description` Бриза в БД уже
есть (~97%) — отдельно НЕ тянем.

## Выбранный набор (15) и правила извлечения

Названия характеристик у Бриз/Daichi/Русклимат разные — матчим по ключевым словам в
`ts.title` (как квиз сайта). Значения «сырые» → нормализуем при выводе.

| # | Подпись в цитате | Бриз `ts.title` | Daichi `ts.title` | Русклимат `ts.title` | Правило значения |
|---|---|---|---|---|---|
| 1 | ⚡ Класс энергоэффективности {A+++} | Класс энергоэффективности EER (охлаждение) | Класс энергоэффективности, охлаждение | ЭНЕРГОЭФФЕКТИВНОСТЬ / Класс энергоэффективности | вынуть класс-токен `[A-G]\+*` |
| 4 | ❄️ Инверторная технология | Инверторная технология (да/нет) | Технология работы (Full DC Inverter/On/Off) | Инверторная технология (Да/Нет) | bool; On/Off → не показывать; запасной детектор по названию позиции (инвертор/inverter), НЕ переопределяя явное «нет» |
| 5 | ⚙️ Компрессор {GMCC} | Марка компрессора | — | — | trim |

| 16 | 📶 Wi-Fi управление | Управление c мобильного приложения по Wi-Fi | Облачные кондиционеры (N/Y) | Управление…Wi-Fi / Wi-Fi модуль | bool; «Ready/Доп.опция» → «Wi-Fi (опция)» |

| 25 | 🌙 Ночной режим (SLEEP) | — | — | Режим SLEEP / Ночной режим | bool |
| 27 | 🔄 Авторестарт после отключения | — | — | Авторестарт при отключении питания | bool |
| 30 | (Русклимат) доп. фишки из поля **УТП** | — | — | УТП (список через `;`) | split `;`, добавить пункты, не покрытые выше |

**Нормализация значений:**
- bool-утверждение: `да|yes|y|1|есть|true|ready|опция|встроен` (без явного `нет|no|n|0|-|отсутств`).
  Для bool-признака пункт показываем только если значение утвердительное.
- min-число диапазона: из `-15 ~ +21` / `-15~24` / `18/20/22` берём наименьшее число.
- класс-энергоэфф.: regex `[A-G]\+{0,3}` (учесть мусор вида `8,50 / A+++`).
- «Wi-Fi (опция)», если значение `ready|доп.опция|опция`; иначе «Wi-Fi управление».

## Формат сообщения

```
💡 <Бренд> <Серия> — ключевые особенности:
<blockquote>
⚡ Класс энергоэффективности A+++
❄️ Инверторная технология
⚙️ Компрессор GMCC
🌡 Работа на обогрев до −15 °C
🔇 Уровень шума от 18 дБ
📶 Wi-Fi управление
🌿 Ионизация воздуха
🛡 Гарантия 36 мес
</blockquote>
```
Порядок пунктов — фиксированный (как список #). Показываем только заполненные/утвердительные.
Если ни одного — «Характеристики уточняются».

## Архитектура (минимальные хирургические изменения)

- **`menu.py`** — ЧИСТЫЕ функции (как уже есть): `build_specs_message(tech_rows, brand, series)` →
  blockquote-текст; набор экстракторов (концепт → keyword-regex + форматтер значения).
  Кнопка: `kb_result_specs(code, bidx, sidx)` → inline-кнопка с callback `c|code|bidx|sidx`.
- **`db.py`** — `fetch_tech_values(nc_codes)` → список `(title, value, source)` (read-only).
- **`bot.py`** — action `c`: resolve серии (как `g`), собрать nc_code позиций, дёрнуть
  `fetch_tech_values`, построить цитату, отправить новым сообщением. Кнопку прикрепить к
  последнему сообщению результата в `_send_result`.
- **`telegram.py`** — `send_photo` принимает `reply_markup` (для кнопки на фото-результате).

## Тесты (без БД и сети)

`tests/test_menu.py` — на РЕАЛЬНЫХ примерах значений из дампа БД:
- извлечение класса из `8,50 / A+++`; min-температуры из `-15 ~ +21`, `-15~24`; min-шума из
  `18,5/25/29`; bool из `да`/`Нет`/`Wi-Fi Ready`/`N`/`Y`/`Доп.опция`;
- порядок пунктов; пропуск пустых/отрицательных; парсинг `УТП` и дедуп;
- сборка цитаты для Бриз-набора и Русклимат-набора (разный состав доступных полей).
