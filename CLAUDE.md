# CLAUDE.md — контекст проекта для Claude Code

## Что это

**Splithub_api_telegram_me** — самостоятельный сервис: раз в сутки собирает список
товаров в наличии и шлёт его владельцу в **личный** Telegram. Один отчёт = строки
вида `• Модель — опт-цена ₽ — количество шт.`, сгруппированные по поставщику,
разбитые на несколько сообщений (лимит Telegram — 4096 символов).

Проект сознательно **отделён** от сайта SplitHome, чтобы деплоиться независимо
(не нужно передеплоивать сайт ради Telegram-задачи).

## Главное: зависимость от сайта

Сервис **только читает** базу сайта SplitHome (PostgreSQL, read-only). Сам он не
синхронизирует поставщиков — данные (товары, остатки, цены) в БД кладёт
синхронизация сайта.

- **Репозиторий сайта:** `github.com/flycited2-dotcom/split-shop_claude` (локально —
  `C:\Users\user\Documents\GitHub\B2B_split_breeze_v2`).
- **Таблицы, которые читаем:** `catalog_product`, `stock_stock`, `stock_warehousestock`.
- ⚠️ **Опт-цена Бриза:** в сайте есть 1-строчный фикс в `apps/sync/tasks.py::sync_stock`
  (пишет `base`/закупку в `price_wholesale` всегда). Без задеплоенного фикса у Бриза
  в БД опт-цена = розничной, и сервис покажет неверную цену. Этот фикс должен быть в
  проде сайта.

## Бизнес-правила отчёта (НЕ менять бездумно)

- **Состав:** «Крым для всех + Бриз со всех складов». Rusklimat/Daichi попадают,
  только если есть остаток в Крыму (склад `Симферополь`); Бриз — на любом складе
  (Крым + материк Шерризон/Ростов). Материк Rusklimat/Daichi НЕ включаем — иначе
  отчёт раздувается почти на весь каталог.
- **Количество:** Бриз — сумма по всем складам; остальные — крымский остаток.
- **Наименование:** `catalog_product.title` как есть (без артикула/НС-кода).
- **Опт-цена:** `catalog_product.price_wholesale`.
- Реализация: фильтр в `stock_report_bot/db.py` (SQL `s.warehouse='Симферополь' OR
  source='breeze'`, `total_qty>0`); количество — `report._qty_for`.

## Структура

```
stock_report_bot/
  config.py    — чтение .env (БД + Telegram), python-decouple
  db.py        — один SQL-запрос остатков к БД сайта (read-only)
  report.py    — сборка текста: группировка/цена/чанкинг, ЧИСТЫЕ функции
  telegram.py  — send_telegram(text, chat_id); charset=utf-8 ОБЯЗАТЕЛЕН
  main.py      — точка входа: fetch → build → send
tests/test_report.py   — unittest на чистом Python (без БД и сети)
docs/PLAN.md
```

## Запуск / тесты

```bash
pip install -r requirements.txt
cp .env.example .env          # заполнить DB_PASSWORD и TELEGRAM_BOT_TOKEN
python -m stock_report_bot.main          # собрать и отправить один раз
python -m unittest discover -s tests -v  # тесты логики отчёта
```

## Конвенции / подводные камни

- **Telegram + кириллица:** отправлять с `Content-Type: application/json; charset=utf-8`
  и `json.dumps(..., ensure_ascii=False)`. Без charset кириллица ломается через
  socat-proxy на VPS (проверено на сайте).
- **Чанкинг:** одно сообщение ≤ ~3900 символов, режем по границам строк.
- **chat_id владельца:** `1264067528` (личный чат). Бот не может написать первым —
  владелец должен был хотя бы раз написать боту.
- **Секреты** (DB_PASSWORD, TELEGRAM_BOT_TOKEN) — только в `.env` (gitignored),
  брать из `/opt/oasis/.env` сайта. В git/доки НЕ коммитить.
- **Расписание:** cron/systemd на 09:00 МСК (примеры в README.md). На сервере сервис
  должен видеть контейнер БД `db` (своя docker-сеть или опубликованный порт).
